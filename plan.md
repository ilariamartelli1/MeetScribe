# MeetScribe: incremental delivery plan

## What we are building

MeetScribe is a local, Dockerized meeting assistant for synthetic or explicitly authorized, non-sensitive test recordings. It starts as a **usable transcription tool**, then gains anonymous speaker labels, evidence-linked draft minutes, saved meetings, and longer recordings. The local MVP milestone accepts WAV/MP3 meetings up to 30 minutes and 500 MB; creates a timestamped, speaker-attributed transcript for processing and optional download; produces topics, decisions, action items, owners and deadlines; supports review and correction of the final summary and TXT/JSON export; saves the original audio for later download; and deletes application-managed meeting data after the agreed retention period. Beyond that milestone, the product should support longer meetings, including two-hour recordings, with limits determined by measurement rather than an assumption of unlimited capacity. In the final browser UI, the summary is the only meeting content displayed and editable; do not display transcript text or speaker-attributed segments anywhere in the browser. Make the transcript available through a non-conspicuous footer download button, for optional verification or debugging, without leaving the summary page. Do not provide a browser audio player or direct browser playback. English is the default recording language, with Italian selectable. Code, comments, UI text, and developer documentation are in English.

The current local app retains the intermediate release's **5 minutes / 100 MB** upload limit and temporary jobs, with transcription and diarization. The normal Docker profile provides transcript-only processing; an optional private Ollama profile adds minutes generation, summary-only editing/review and TXT/JSON export. The front page does not display transcript text or speaker labels, and normal job-status responses omit transcript results; a low-prominence footer button downloads the transcript without leaving the page. The uploaded audio is removed after transcription. Results remain in memory for up to one hour and are not restored on refresh/restart. Accounts, persistent meetings, saved audio and the planned seven-day retention are not implemented.

## Delivery rule: one small change per prompt

- Each numbered slice below is **one human-reviewable implementation request**, not an entire sprint. When asked to "start" or "continue," implement only the next unfinished slice, including its automated tests, the smallest relevant test run, and the matching README/plan update. Stop and explain what changed, why it is designed that way, and what the tests establish. Do not silently proceed to another slice or sprint.
- Leave each tested change **uncommitted for human review**. Do not start another slice while the previous change awaits approval; first address requested revisions or obtain explicit approval. On approval, commit and push only that approved change to GitHub. As the last change before committing and pushing, remove its "awaiting review" marker and, if there is a following step, mark the next step "next step"; make no other status edits. Keep each commit scoped to its reviewed, tested behavior. Never commit tokens, meeting recordings, model weights, database files, or local configuration. Small, explicitly generated synthetic audio fixtures may be versioned for tests.
- Keep slice IDs stable and record completed checkpoints in this plan as they are verified. Fakes and small fixtures test contracts in CI; any slice introducing a model also requires an explicit local real-model smoke check before calling its checkpoint complete. If hardware/setup blocks that check, report the checkpoint blocked rather than claiming success.
- A new code path needs a relevant test in the same slice. Prefer unit/API tests first, add browser or Docker tests where the behavior crosses those boundaries, and use only authorized, non-sensitive audio for real-model checks. Quality thresholds for WER/DER and correction time are set **after** measuring a baseline, not guessed ahead of time.

## Code organization

- **Application folder grouping.** Organize provider
  integrations under `app/adapters/`, meeting-processing contracts and
  coordination under `app/core/`, and configuration and runtime support under
  `app/infrastructure/`. Keep the API and container startup entry points in
  place. This move preserves existing behavior and does not by itself remove
  existing provider or infrastructure dependencies from the core.
- **Provider-independent pipeline boundaries.** Supply
  spawn-compatible speech-model factories to the core jobs and translate
  provider-specific minutes requests, responses and budget configuration at
  the adapter boundary. Retain the current providers, fail-fast context budget,
  shared GPU gate, cancellation and release behavior. ASR-specific provenance
  remains available through the faster-whisper adapter while other providers
  can supply their own provenance fields. Unit tests cover the boundaries;
  real-model, browser and Docker integration checks have not been rerun.

## Architecture choices and why

- **Keep the system small.** Python/FastAPI serves a versioned JSON API (`/api/v1`) and plain HTML/CSS/JavaScript. Use one API process with a bounded coordinator and a stoppable child process for each inference job; this keeps the browser responsive and permits real cancellation without leaving a native model call running. Do not start a new GPU job until the old child and any local model-server request have stopped. No broker, distributed worker fleet, vector database, agent framework, or React dependency for the local MVP. A later React client can consume the same API.
- **Introduce replaceable model boundaries only as they are used.** Define typed, framework-independent transcript segments, diarization turns, and minutes. Add ASR, diarization, and summary adapters when their respective sprints begin; retain model/version/settings provenance in results. Compare alternatives on the same fixtures, not model file size alone. For the first release, try faster-whisper `large-v3-turbo` on a tested INT8-compatible GPU compute setting; reject unavailable CUDA with an actionable error. CPU mode must be an explicit, tested choice, never a silent fallback.
- **Do not filter twice or change the timebase without accounting for it.** Start with faster-whisper's integrated Silero VAD rather than a second independent VAD pass. Use conservative settings and tests for quiet negations and silence. Preserve timestamps on the original recording. Later, pyannote independently processes the audio (not the transcript); align its speaker turns to ASR timestamps afterward. Run heavy GPU stages sequentially on this 6 GB VRAM laptop.
- **Package for portability, not premature production.** Docker Compose initially runs only the app. Add an internal-only Ollama service when minutes generation exists; publish only the app to host `127.0.0.1`, not Ollama. Bind correctly inside containers, validate Host/Origin and protect state-changing requests against cross-site submission; use local persistent volumes only when storage is introduced. Docker moves software, not GPU drivers, credentials, authorization, security policy, or operating capacity: company-VM deployment and real company recordings require separate approval and work. "Voice 1" labels are not anonymization or recording consent.
- **Keep inference on premises.** Downloads of pinned weights are allowed during separate provisioning, but no audio/transcript goes to third-party inference. Restrict runtime adapters to pinned local model paths and the explicitly allowlisted internal Ollama endpoint (`http://ollama:11434`); reject configurable remote endpoints instead of trusting a URL supplied by a client. Keep setup tokens out of images and runtime configuration. Verify the pinned versions support and use cloud/telemetry-off and offline settings (including `OLLAMA_NO_CLOUD=1`, `PYANNOTE_METRICS_ENABLED=0`, `HF_HUB_DISABLE_TELEMETRY=1`, and `HF_HUB_OFFLINE=1` when applicable). A private Docker network alone is not an egress firewall: run a post-provisioning job with outbound traffic blocked before claiming offline operation.
- **Limit browser retention.** Return `Cache-Control: no-store` on transcript, meeting, audio and export responses; do not put content in localStorage, IndexedDB, service workers, or external CDNs. Keep scripts/assets local, enforce a restrictive content-security policy, render model text as text rather than HTML, and clear temporary browser media URLs when no longer needed. Browser downloads and host backups remain outside app deletion control.
- **Pin, then update deliberately.** Lock transitive Python dependencies, container image digests and model revisions/digests, with a record of licenses and compatible CUDA/audio-library versions. Keep each model's artifact hashes in its versioned application manifest and verify them with the shared integrity checker before loading. Check security advisories and licenses at each release checkpoint and before company deployment; update a dependency/model in its own reviewed slice, then rerun the affected tests, Docker smoke check and real-model quality check. Do not use unattended `latest` upgrades or assume pinning alone is maintenance.
- **Make uncertain outputs visibly uncertain.** Anonymous speakers are not identified people; overlap can be marked unknown. A JSON schema and a real source ID prove neither factual support nor completeness. Minutes are drafts until reviewed; owners/dates not explicitly supported stay "not specified," and relative dates are not silently resolved using upload time. Users correct the summary, decisions, action items, owners and deadlines rather than editing transcript text or speaker labels. Bind citations to the exact transcript revision; replacement or regeneration of the source transcript marks generated minutes stale, and minutes regeneration is deliberate. Do not overwrite human edits or present stale material as reviewed.

Report already-finished/unknown jobs clearly; cancellation is not a request to delete an already exported transcript. *Check:* fake jobs cover cancellation during model load and inference, a late result, repeated cancel, forced termination, retry after a termination error, freed job slot and responsive status requests.

**1.3 Bounded upload endpoint (committed; stereo support extended).** Stream WAV/MP3 into a generated temporary path; bound multipart parts/request bytes, duration (5 minutes), size (100 MB), decoder time, decoded samples and supported channels; reject corrupt/empty/unsupported files before starting work. **1.4 Minimal browser flow (committed).** Added an accessible plain-JS page for language choice, upload/status/errors, a Cancel button, timestamped segment text and client-side TXT draft download. Use a restrictive content-security policy and local-only assets. *Check:* browser/API tests cover upload -> read-only display -> download, cancel during processing, accepting and declining result replacement, visible recording-use notice, failure display, draft labeling, safe rendering and no persistent browser content.

## Sprint 3 - Draft structured minutes

**3.1 Private local summary model (implemented and verified).** Added an opt-in, digest-pinned Ollama Compose service and provisioned the Apache-2.0 Qwen3 4B Q4_K_M artifact. The offline app-to-Ollama smoke completed with all 37 model layers and the 4,096-token KV cache on the development GPU; see [the slice report](docs/reports/sprint-3-slice-3.1.md) for digests, runtime settings, measurements and limitations.

**3.2 GPU handoff (implemented and measured).** A parent-owned shared gate serializes spawned ASR/diarization jobs and all Ollama requests. Ollama runs one request/model, requests `keep_alive=0`, streams cancellation and verifies unload before releasing the gate; uncertain cleanup blocks later GPU work. The offline final-container ASR -> GPU diarization -> Ollama -> ASR test passed, including concurrent generations and cancellation. The corrected run peaked at 3.36 GiB total GPU use and 11.1 GiB host RAM; swap peaked at 5.12 GiB from a 4.28 GiB baseline. This is a single synthetic-fixture observation, not a capacity claim; see [the slice report](docs/reports/sprint-3-slice-3.2.md) for per-stage timing, memory, sampling and limitations.

**3.3 Minutes schema and evidence checks (implemented).** Added strict typed response models and the versioned export-v1 contract. Response shape, completeness, citation IDs, named-owner/speaker separation and deadline evidence are checked independently; relative or ambiguous dates are never normalized from upload time. A valid citation is not treated as proof that its claim is true. The targeted checks passed 28 tests; the default suite passed 233 and skipped 30 opt-in tests. See [the slice report](docs/reports/sprint-3-slice-3.3.md) for boundaries and limitations.

**3.4 Bounded extraction (implemented).** Added a replaceable extractor protocol and Ollama adapter, configured to the measured 4,096-token context rather than Qwen3's advertised maximum or an implicit default. The adapter bounds the complete prompt using its UTF-8 byte length plus a 128-token template reserve, reserves at most 768 generated tokens, and includes every transcript segment and a compact output-shape example; the full Pydantic schema is supplied as Ollama's structured-output format. It fails before inference if the complete input cannot fit and does not split transcripts or return partial drafts. Thinking is disabled by the existing client. The adapter rejects incomplete or length-stopped responses, validates only the final answer and compares runtime token counts against the configured budget. Transcript text is treated as untrusted data, not instructions. The focused tests passed 18 cases; the default suite passed 251 and skipped 30 opt-in tests. Only fake-client extraction has been run, so the template reserve and runtime count comparison still need a real extraction check in 3.7. See [the slice report](docs/reports/sprint-3-slice-3.4.md) for limits and test results.

**3.5 Edit and export draft minutes (implemented).** The browser displays and edits only the summary, topics, decisions, action items, owners and deadlines. Removed the interim transcript display; normal job-status responses omit transcript results, and the original explicit download used a separate low-prominence page. Users can save edits, mark the current minutes revision reviewed, and download TXT/JSON exports with the matching **DRAFT / UNREVIEWED** or **REVIEWED** state. TXT contains minutes only; JSON export v1 intentionally includes the source segments and anonymous speaker IDs required by its contract. Human-added items may have no citation; manual edits remain drafts until explicitly reviewed and do not receive model-evidence validation. Focused API/unit/assets and browser tests cover editing, review/revisions, exports, privacy boundaries, safe rendering, transcript download and Unicode. The real model/audio-to-minutes checkpoint remains for 3.7; see the [slice report](docs/reports/sprint-3-slice-3.5.md).

**JSON export v1 contract (schema implemented in 3.3; end-to-end export in 3.5).** UTF-8; `schema_version` is `1`; `meeting_id` is the temporary job ID until persistent meeting IDs arrive in Sprint 4; `language` is `en` or `it`. `start_ms`/`end_ms` are integer milliseconds on the original recording timeline, with `0 <= start_ms < end_ms <= duration_ms`. Segment IDs are stable within a transcript revision; citations use those IDs. The `segments` array is the exact source revision cited by the minutes, identified by `minutes_source_transcript_revision`; `transcript_revision` identifies the latest source. A nullable `speaker_id` means attribution is unknown. `review_status` is `"DRAFT / UNREVIEWED"` or `"REVIEWED"`; summary edits and source replacement invalidate review, and `stale` indicates that minutes were generated from a different transcript revision. TXT and JSON exports must identify stale minutes. These status and revision fields must be computed from the same authoritative state as the exported contents, never supplied by the LLM.

```json
{
  "schema_version": 1,
  "meeting_id": "meeting-123",
  "language": "en",
  "review_status": "DRAFT / UNREVIEWED",
  "stale": false,
  "transcript_revision": 1,
  "minutes_revision": 1,
  "minutes_source_transcript_revision": 1,
  "segments": [
    {
      "id": "segment-1",
      "start_ms": 1000,
      "end_ms": 2500,
      "speaker_id": "voice-1",
      "text": "What about the new document draft?"
    },
    {
      "id": "segment-2",
      "start_ms": 2600,
      "end_ms": 4500,
      "speaker_id": "voice-2",
      "text": "I'll send it next Friday."
    }
  ],
  "minutes": {
    "summary": "Voice 2 will send the new document draft next Friday.",
    "topics": [
      {
        "text": "The new document draft",
        "source_segment_ids": ["segment-1"]
      }
    ],
    "decisions": [],
    "action_items": [
      {
        "description": "Send the new document draft",
        "owner_name": null,
        "owner_speaker_id": "voice-2",
        "deadline_text": "next Friday",
        "deadline_date": null,
        "source_segment_ids": ["segment-1", "segment-2"]
      }
    ]
  }
}
```

With this context, the intended action description resolves "it" to "the new
document draft" and cites both source segments. The extractor sends all
transcript segments when the complete prompt fits the context budget; this is
contextual model output, not behavior guaranteed by the JSON schema. Evidence
checks validate citation IDs and owner/deadline evidence, not whether the
description resolves the pronoun correctly, so human review remains necessary.

`owner_name` is a person explicitly named in the recording; `owner_speaker_id` is an anonymous speaker only when attribution is supported, never an inferred real identity. `deadline_text` retains the source wording; `deadline_date` is an ISO `YYYY-MM-DD` date only when unambiguous. For no spoken deadline both are `null`; for an ambiguous/relative deadline only `deadline_date` is `null`. Unknown owners likewise use `null`, displayed as "not specified" in the UI. Arrays may be empty, but required keys remain present. Before JSON export is wired to the API in 3.5, test null semantics, original-audio time units, cited revision integrity and round trips; changing these fields later requires a new `schema_version`. Reject unsupported export versions clearly; if importing old versions is added later, use an explicit, tested migration rather than silently reinterpreting their fields.

**3.6 Summary regeneration and stale-source handling (implemented).** When the attributed source for a job changes, increment its transcript revision, mark existing minutes stale and clear review; do not regenerate automatically. Keep the exact source revision cited by existing minutes so stale exports cannot silently bind old citations to new segment text. Add an explicit regeneration action; require confirmation before replacing saved human edits, publish replacement minutes only after successful validation, and preserve the previous draft on failure or cancellation. Stale minutes remain visibly stale and cannot be marked reviewed; transcript/speaker correction is not offered in the UI. *Check:* source-revision change, concurrent summary edit, stale-citation, failed/cancelled regeneration and no-overwrite tests. The focused manager/API suite passed 29 tests; the browser suite passed 10; the default suite passed 271 and skipped 30 opt-in cases. See the [slice report](docs/reports/sprint-3-slice-3.6.md).

**3.7 Minutes checkpoint (incomplete).** Added the opt-in offline evaluation harness and extraction-token metrics. The approved Docker/GPU run transcribed the 297-second English checkpoint, but minutes generation correctly failed before inference: its conservative total context estimate (prompt upper bound plus reserved generation tokens) was 11,322 tokens, exceeding the configured 4,096-token context. The Italian and known-ASR-error cases were not reached; no draft, real extraction-token counts or resource report was produced, and correction time was not measured. By user decision, keep the fail-fast behavior; do not add transcript chunking or change models/context in this slice. Earlier minutes-quality runs passed 12 checks across six frozen transcripts and all 6 checks on the real two-voice fixture, but do not resolve the 297-second context limit or the ASR substitutions `Fragi`/`Elina`. A later weekday-normalization experiment is isolated on branch `llm-normalize-python-summary`, not in `main` and not approved as the project flow. It normalizes explicit weekday typos only in derived minutes; the original transcript remains unchanged, and no calendar date is inferred. `Elina` is not auto-corrected. Slice 3.7 remains incomplete until over-budget meetings are enabled and validated. Never infer that deterministic minutes normalization improves ASR accuracy or that schema/citations eliminate hallucinations. **A user now has a complete, explicitly unreviewed meeting draft only when the full transcript fits the configured context.** See [minutes context scaling and limitations](docs/investigations/minutes-context-scaling.md) for current evidence and follow-up questions, and [minutes retrieval options](docs/architecture/minutes-retrieval-options.md) for an exploratory comparison of chunking and RAG approaches. These options are not selected or implemented.

## Sprint 4 - Saved meetings, audio download and honest retention

**4.1 Persistent meeting records (next step).** Introduce SQLite migrations, local audio/results volumes, meeting IDs and model provenance. Save the original uploaded audio and drafts across restarts from this point forward for later access until deletion or expiry; temporary-session results from earlier releases are not migrated. Keep the DB on a local persistent volume: enable WAL and `synchronous=FULL` for durable commits, `foreign_keys=ON` and a bounded `busy_timeout` on every connection; use connections owned by one execution context, short transactions outside inference, and versioned migrations that reject an unsupported newer schema. No live-file-copy backups. *Check:* save/restart/reload/migration tests, concurrent reads/writes, lock timeout and disk-full errors, and proof recordings remain outside the web root.

**4.2 Persistent worker ownership.** Use a single Uvicorn API process (no multiworker or auto-reload in Docker) and take a nonblocking, exclusive Linux file lock in the same local data volume at startup; a second app instance sharing that volume fails startup clearly. Atomically claim SQLite jobs by status/attempt ID, so a stale attempt cannot publish after restart; release the file lock automatically on process exit. Define bounded retries only for identified transient failures; mark non-retryable errors failed. Publish staged artifacts using temporary names and atomic rename, reconcile orphaned files on startup, and checkpoint job state at stage boundaries without a transaction held during inference. Never restart an attempt until its former owner is confirmed gone. *Check:* launch two app instances against one volume; inject interruption immediately before/after artifact rename and DB commit, transient/permanent failures, and crash/restart during each stage. Verify no duplicate GPU job, stale publication, partial complete state or leaked orphan; keep status responsive.
